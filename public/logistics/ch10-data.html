"接个口"这件事，法律上被拆成了好几层：传输的是什么数据（是不是个人信息）、谁决定用途（控制者）、谁只是帮忙处理（处理者）、数据要合法地"出国"走哪条路径、出问题怎么通报。这四层没想清楚，IT 把接口一开，公司的合规责任就跟着数据一起"出境"了——而 GDPR 的罚则是全球营业额 4%，不是运费那点钱。

就好比：你为省两百块运费没买保险，结果货值四百万的柜子没了——省的是小钱，赌的是身家。
就好比：你以为"物流数据"只是快递单，其实从下单到签收再到退货，整条链都在记"谁、寄给谁、送到哪、要不要退"——这些拼起来就是一份客户档案。 就好比：数据出境不是"传一次就完"，而是"从此在境外也有一份副本"，后面每一步处理都要按两边规矩来，想撤回都难。

一、物流链条上到底有哪些个人信息

很多人以为"物流数据"就是面单上那几个字。其实从你下单到买家签收、再到售后，整条链上至少沉淀了五类个人信息。每一类出境的法律性质都不一样，不能混着算。

大白话打比喻

这票货的物流数据，好比你给外地的朋友寄了一箱礼品，还要在对方城市找个"代收点"代管、再让"跑腿"送上门：面单是写有朋友电话地址的快递单，轨迹是你和朋友都能看到的"到哪儿了"，签收记录是跑腿拍的"已送达"照片，客户画像是你根据这些寄递记录给朋友打的标签（比如"喜欢贵价礼盒"），售后记录是后来退换货时留的对话。你把这些全部交给境外的代收点和跑腿，等于把一整本"朋友通讯录 + 行为日记"送出了国——这当然不是"接个口"那么简单。

面单信息收件人姓名、电话、详细地址、邮编、可能含"小心易碎/高价值"备注你（托运人）制单时填写，传给货代、船公司、海外仓、末端派送必然出境（目的地在欧盟）高：直接可识别到个人

大白话：只要数据里能直接或间接认出"这是哪个具体的人"，它就是个人信息；一旦这份数据被传送到中国境外（含港澳台以外的服务器、境外主体的系统），就触发《个人信息保护法》关于跨境传输的合规义务，以及欧盟侧 GDPR 对"数据出口"的要求。具体门槛与路径以现行规定为准。

就好比：你家门禁卡上写了"3 栋 502 张三"，这是直接识别；只写"3 栋 502"虽没名字，但结合物业名册也能找到人，这就是间接识别——两种都算"个人信息"，出境都要管。
个人信息Personal Information
以电子或其他方式记录的、可单独或与其他信息结合识别特定自然人的各种信息。《个人信息保护法》相关规定对"可识别"采宽口径，昵称、设备号、位置都可能落入。
控制者Controller
决定处理目的与方式的一方。在 NG-2026-017 里，霓光作为卖家，决定"为了把货送到买家手里而收集并使用这些信息"，它通常就是控制者。
处理者Processor
受控制者委托、按控制者的指示处理个人信息的一方。WareHub 仓库、末端派送商如果只是按指令收发/存储面单，是处理者；若它自己决定怎么用这些数据做营销，就又成了控制者。
受托处理方Entrusted Processor
《个人信息保护法》语境下"受托处理个人信息的受托人"。与 GDPR 的 Processor 概念对应，但对外责任仍主要由控制者承担，受托人仅在过错范围内负责。
跨境传输Cross-border Transfer
个人信息从中国境内提供给境外组织、个人，或境外可访问境内存储的个人信息。三条常见路径见第三节，门槛与程序以现行规定为准。
数据最小化Data Minimisation
只收集、只传输实现目的所必需的最少字段、最短期限。面单上别顺手把买家生日、会员等级也传出去——多传一个字段，多一分责任。
留存期限Retention Period
数据"用到什么程度就该删"。面单、轨迹不是留得越久越好；超过必要期限应删除或匿名化，否则构成过度留存。
数据主体权利Data Subject Rights
个人对其信息的查询、更正、删除、携带、拒绝等权利。GDPR 下尤为完整；控制者须设计"协助机制"，不能把球踢给海外仓。

二、谁是谁：控制者与处理者（中英对照）

把 NG-2026-017 的链路拆开，你会发现同一个海外仓 Kevin，在不同场景下身份会变。这正是跨境物流数据合规最容易踩坑的地方：你以为签一份合同就万事大吉，其实身份没写清，责任就糊在中间。

关键判断就一句话：谁决定"为什么用这些数据、怎么用"，谁就是控制者；谁只是"照着别人写的说明书操作"，谁就是处理者。身份没写清，责任就真空。身份写反了，后果是：该做的安全评估没做、该签的 DPA 没签、出事时互相说"是对方决定的"。

就好比：你雇保洁来家里打扫（处理者），你决定"擦桌子、别动抽屉"（控制者）；如果保洁自己翻你抽屉、把照片发朋友圈，那她就不再是"按指示做事的人"，而变成了另一个"自己做主的人"——责任完全变了。

个人信息要从中国出境，依现行《个人信息保护法》及《促进和规范数据跨境流动规定》相关规定，存在若干合法路径。具体哪条适用、门槛是多少（如是否达到特定数量阈值），以最新规定为准，本章不提供具体人数数字。实务中常见的三类路径如下，但务必落地前核对现行文本。

就好比：过海关有"红色通道、绿色通道、免申报通道"，走哪条看你怎么带、带多少；别凭感觉闯，先看清标志。

大白话：出境有"三条正路"：要么走官方安全评估（大票、敏感走这条），要么签官方标准合同并备案（中小票常用），要么落在法定豁免里。哪条都行，但不能"什么都不做直接传"。具体落到你这笔量，要走哪条，以最新规定为准、必要时咨询数据合规律师。

就好比：你要带一箱东西出国，要么报关走正式通道（安全评估），要么填张申报单备案（标准合同），要么属于"自用合理数量免申报"那类（豁免）——但"我忘了"不属于任何一条合法通道。 就好比：货一到欧盟境内，就像进了另一套小区物业规则——你在家怎么管钥匙是一套，人家小区怎么管门禁是另一套，两套都得守。

四、欧盟侧 GDPR 下的角色划分与 DPA 要点

即便中国侧出境路径走通了，数据一到欧盟，GDPR 就要管。GDPR（General Data Protection Regulation，通用数据保护条例）2018-05-25 起适用，核心要求之一是：控制者与处理者之间必须有一份书面协议，也就是 DPA（Data Processing Agreement，数据处理协议）。霓光作为把数据带进欧盟的控制者，和 WareHub 作为处理者，这份 DPA 不能省。

高频红线

GDPR 第 28 条（以现行文本为准）要求处理者"仅在控制者书面指示下处理"；没有书面 DPA 而让处理者动个人数据，控制者自身先违规。所以不是 WareHub 催你签，是你自己需要这份纸。罚则层面，GDPR 最高可处全球年营业额 4% 或 2000 万欧元（以高者为准，具体以条文为准）——这跟"运费省两千"完全不在一个量级。

DPA（Data Processing Agreement，数据处理协议）至少应覆盖以下要点，建议逐条对照、缺一条补一条：

  • 处理目的与方式：明确"仅为履行 NG-2026-017 的仓储、拣货、派送而处理面单信息"，禁止挪作营销或转售。
  • 处理期限：约定合同终止后 X 个工作日内删除或返还全部个人信息及衍生数据（见第六节留存期限）。
  • 子处理者：WareHub 如要再委托末端派送商，须事先书面告知并取得同意，且 WareHub 对子处理者行为向霓光负责。
  • 安全措施：加密传输与存储、访问控制、日志审计、漏洞管理，写清最低标准与认证要求。
  • 数据主体权利协助：约定 WareHub 在收到查询/更正/删除请求时的通知时限与配合义务，控制者不能把球踢给仓库。
  • 审计权：霓光有权定期或事件驱动地审计 WareHub 的数据处理活动，含调取日志。
  • 删除与返还：终止时须出具删除证明；拒不删除的违约责任。
  • 跨境传输机制：若 WareHub 进一步把数据传出欧盟，须依赖 SCC（Standard Contractual Clauses，标准合同条款）等合法机制，并在 DPA 中载明。
就好比：DPA 就是你们两家就"客户通讯录"签的《借用公约》：只能用来送快递、不能拿去加微信卖货、用完必须销毁、借给第三方要打招呼、丢了要马上报——白纸黑字，谁违规章谁。

五、八组法务对话（本站核心）

对话 1「不就是个接口吗，让 IT 搞一下」
周总

「ERP 接 WMS，不就是让 IT 开个接口？怎么还扯上法律了？」

法务

「接口一开，几万条欧洲买家的姓名电话地址就实时传到荷兰服务器了——这是一次个人信息的跨境传输，不是技术动作，是法律行为。」

周总

「有这么严重？」

法务

「欧盟那边的 GDPR 罚则是全球营业额的 4%。咱们这票货值 480 万美元，可公司年营收远大于此，真出事不是运费那点钱能补的。所以先定路径、再开接口。」

条款翻译

《个人信息保护法》相关规定要求个人信息出境具备合法路径；同时 GDPR（General Data Protection Regulation，通用数据保护条例）要求控制者与处理者之间有书面协议。两边规则叠加，接口上线前必须完成：出境路径评估 + 与 WareHub 签署 DPA。

就好比：你说"不就是把客人名册复印一份放分店嘛"，但分店在海外、当地法律管得极严，复印那一刻你就已经"把名册带出国"了——先办护照（合规路径），再复印。
对话 2「面单信息也算个人信息？不就几个字」
阿杰（业务）

「面单上不就收件人姓名电话地址嘛，这也算个人信息？」

法务

「算，而且是最典型、最直接可识别的个人信息。姓名 + 电话 + 地址，三样凑齐，任何一个欧洲买家都能被精确定位到门牌。」

阿杰（业务）

「那轨迹、签收这些呢？」

法务

「轨迹和签收是间接识别 + 行为素材，结合面单一样能锁定个人；客户画像更是'衍生个人信息'。五类都算，不能挑着管。」

条款翻译

《个人信息保护法》对"个人信息"采"可单独或与其他信息结合识别特定自然人"的宽口径。面单、轨迹、签收、画像、售后五类均落入，处理前需有合法基础与告知。

就好比："地址 + 电话"等于把别人的家门钥匙形状画了出来；单独一把钥匙坯打不开，但配上"这把钥匙开 3 栋 502"的标签，就够了。
对话 3「出境要走哪条路？安全评估还是标准合同」
法务

「依法有三类的常见路径：安全评估、标准合同备案、或法定豁免情形。具体咱们这笔量走哪条、门槛数字多少，以《促进和规范数据跨境流动规定》最新文本为准，我不给你编个数字。」

周总

「那我怎么知道用哪条？」

法务

「先做一次'数据盘点 + 出境路径判定'：传什么、传给谁、多少人、什么类型。判定结论出来再选路径、备材料。这一步不能省，否则备案报错了也是退回来重来。」

落地动作

建议流程：① 盘点字段与量级；② 对照现行规定判定适用路径；③ 走对应程序（评估/标准合同备案/豁免留痕）；④ 配套个人信息保护影响评估（PIPIA）。所有结论以现行规定为准，必要时咨询数据合规律师。

就好比：出国带东西，先称重量、看品类，再决定走"报关通道"还是"申报单"还是"免申报"——不问重量直接闯，过关时才知道错了就晚了。
对话 4「Kevin 说他们模板合同不能改，DPA 怎么办」
Kevin（WareHub）

「我们的海外仓主协议是标准模板，DPA 条款已经内置，不能单独改。」

法务

「内置可以，但请确认它覆盖了八要件：目的、期限、子处理者、安全措施、权利协助、审计、删除返还、跨境机制。缺哪条，我们补一份 DPA 附件，附件优先于模板。」

Kevin（WareHub）

「子处理者那条，末端派送商我们一定会用，能写死吗？」

法务

「可以写'事先书面列名 + 一般授权'，但你要承诺对子处理者行为向我方负责，并且子处理者也要签同等级 DPA（flow-down）。」

条款翻译

GDPR（General Data Protection Regulation，通用数据保护条例）下，处理者再委托（子处理）须有控制者授权，且通过合同将相同的数据保护义务传导给子处理者。建议写明：乙方委托子处理者须经甲方书面（含邮件）同意；乙方对子处理者违约向甲方承担连带责任。

就好比：你把家门钥匙给了保洁，保洁又转交给她同事——你得事先同意，而且保洁要对她同事的行为负责，否则钥匙被乱用你只能找保洁。
对话 5「我们到底是控制者还是处理者」
阿杰（业务）

「WareHub 也在用我们的数据，他们算共同控制者吗？」

法务

「就'把货送到买家'这个目的，我们决定目的、他们照做，我们是控制者（Controller）、他们是处理者（Processor）。但若 WareHub 拿这些数据自营增值服务、自己定用途，那段它就是另一层的控制者。」

阿杰（业务）

「那身份写反了会怎样？」

法务

「写反了，责任就糊在中间：该我们做的出境合规没做、该他们签的 DPA 没签，出事互相踢。所以主协议里第一句就写清身份。」

条款翻译

建议主协议写明：就 NG-2026-017 项下为履行仓储与派送而处理的个人信息，甲方（霓光）为个人信息处理者/控制者，乙方（WareHub）为受托处理方/处理者；乙方如就同一数据另定处理目的，应事先书面通知甲方并另行取得合法基础。

就好比：婚庆公司帮你筹婚礼（你是导演、它是执行），它若私下用你的宾客名单去拉自己的婚庆客户，那一段它就变成了"自己的导演"，要为那段负责。
对话 6「数据最小化，面单能不能少传点」
法务

「能，而且应该。面单只传履约必需字段：收件人、电话、地址、邮编。买家生日、会员等级、消费偏好，别顺手带出去——多传一个字段，多一分责任、多一个泄露面。」

阿杰（业务）

「可是仓库说要会员等级才能分优先级发货。」

法务

「那就让仓库用我们给的'优先级代码'而非原始会员等级，原始数据留在境内。这叫'去标识化后传输'。」

条款翻译

数据最小化（Data Minimisation）是 GDPR 原则之一，也是《个人信息保护法》"最小必要"精神的体现。建议在 DPA 中列明字段白名单，超出白名单的传输须事先书面同意。

就好比：去健身房只办"进门 + 淋浴"的卡，别顺手把家庭住址、工资条也复印给前台——他用不上，还增加泄露风险。
对话 7「数据留多久？仓库说一直存着更方便」
Kevin（WareHub）

「数据一直留在我们系统里，下次发货更方便，不用重新传。」

法务

「方便是它的，风险是你的。超过必要期限必须删除或匿名化。建议面单数据在妥投 + 售后异议期满后删除，轨迹数据按运维需要短留。」

Kevin（WareHub）

「那我们要保留日志做审计怎么办？」

法务

「日志可以留，但要做访问隔离与最短化，且明确'仅为安全审计、不得用于其他目的'。删除义务和日志留存是两个动作，分开写。」

建议留存周期（以业务实际与现行规定为准，非强制天数）

① 面单信息：妥投并完成售后异议处理后删除/匿名化；② 运输轨迹：运维与争议所需最短周期；③ 签收记录：与面单同周期或依税务/争议需要；④ 客户画像与售后：目的实现即删，营销用途须另行告知同意。

就好比：超市小票留一个月对账够了，非要留三年，等于把你的购物清单长期摊在柜台上——方便了柜员，危险了你。
对话 8「系统对接的技术与合同要点，到底要管哪些」
法务

「技术点和合同点要一起管：API（Application Programming Interface，应用程序接口）权限最小化、全量日志、传输加密、访问控制、事件通知。接口不是'通了就行'，是'谁能在什么范围看什么'。」

周总

「这些 IT 懂就行了吧？」

法务

「IT 管实现，法务管'写在合同里的承诺'：WareHub 须承诺加密标准、日志保留期、异常 24 小时内通知、配合安全事件调查。没写进合同，IT 做得再好也没法追责。」

条款翻译

建议在 DPA 与接口附件中列明：传输采用 TLS 1.2+ 加密；API 采用最小权限令牌并按角色鉴权；双方保存处理日志不少于 X 个月；发生数据泄露或未经授权访问，接收方须在 24 小时内书面通知控制者。

就好比：你给分店配了监控（日志）、装了门锁（加密）、只给店员开自己工位的钥匙（权限），但还得在合同里写"门锁坏了 24 小时内报总部"——否则锁坏了没人说，丢了算不清。

六、就地展开的详解（点开就看，不跳走）

术语常见坑个人信息的"可识别"到底怎么算？

大白话

只要数据能让你"认出这是哪一个具体的人"，或者拼上别的资料能认出，就是个人信息。不是非得写全名才算。

专业术语

个人信息（Personal Information）、《个人信息保护法》"可单独或与其他信息结合识别特定自然人"；GDPR（General Data Protection Regulation，通用数据保护条例）的"identified or identifiable natural person"。间接识别、衍生画像均落入。

条款解析

建议在《数据出境清单》中逐字段标注"直接/间接识别"与"是否必需"，作为最小化与出境路径判定的基础。跨境物流场景下面单（直接）、轨迹（间接）、签收（直接+间接）均须纳入。

生活比方

门牌号单独看只是数字，配上小区名和住户表就是"谁家"；数据也一样，组合起来能认人，就受个保法管。

常见坑"IT 开了接口，合规就自动完成"是最大误区

大白话

接口通了只是"管道通了"，管道里流的是受保护个人信息，这事本身要单独合规：出境路径 + DPA + 影响评估，一个都不能少。

专业术语

数据出境路径（安全评估 / 标准合同备案 / 豁免）、个人信息保护影响评估（PIPIA）、DPA（Data Processing Agreement，数据处理协议）、GDPR 第 28 条书面协议要求。

条款解析

上线前 checklist：① 出境路径已定并履行；② 与 WareHub 签署 DPA 且覆盖八要件；③ 完成 PIPIA 并留存；④ 字段最小化白名单生效；⑤ 日志与事件通知机制写入合同。

生活比方

水管接好了不代表水能合法用——还得有取水许可、水质检测、用水合同，否则一开水龙头就违规。

术语什么是 SCC（Standard Contractual Clauses，标准合同条款）？

大白话

当数据从欧盟再传出，或欧盟处理者向第三国提供数据，可用欧盟委员会发布的"标准合同条款"作为合法传输机制——相当于一份官方背书的"数据护送函"。

专业术语

SCC（Standard Contractual Clauses，标准合同条款），是 GDPR 下跨境传输的常用合法机制之一；与中国的《个人信息出境标准合同》是两套不同体系，不能互相替代。

条款解析

在 DPA 中约定：若 WareHub 或子处理者将个人数据进一步传出欧盟 / 欧洲经济区，须依赖有效的 SCC 或其他 GDPR 认可的传输机制，并向控制者提供副本。

生活比方

中国的"出国申报单"和欧盟的"出境护送函"是两张不同的纸，去不同关境用不同的；不能拿一张当两张使。

常见坑数据事件应急：丢失、泄露怎么通报

大白话

一旦发生泄露或丢失，别先想着捂：控制者要能及时知道、及时通报、及时记档案。拖延通报在 GDPR 下本身就是违规。

专业术语

数据安全事件（Security Incident）、个人数据泄露（Personal Data Breach）、通报时限、事件记录（Record of Processing Activities）。具体时限以 GDPR 与《个人信息保护法》现行规定为准，本章不编造具体小时数。

条款解析

DPA 应写：接收方发现或合理怀疑事件后，在约定短时限内（建议 24 小时）书面通知控制者；控制者负责对外依法通报；双方共同保存事件调查与处置记录。

生活比方

家里漏水了，先关阀、叫物业、留照片台账；不是先拿抹布擦干假装没事——等楼下上来敲门，责任更大。

就好比：同一份接口文档，写清"谁控制、怎么用、用多久"就像把借出去的钥匙登记在册；不写，就等于把钥匙随手塞给陌生人。

七、案例卡：同一件事，两种写法

案例：ERP ↔ WMS 对接条款的两种写法（教学改编，案号虚构）
✗ 常见写法（出事就扯皮）

"双方系统对接，数据实时同步至荷兰服务器，WareHub 按运营需要存储与使用相关数据。"
问题：没写谁控制、没签 DPA、没限制用途、没删期、没事件通知、没子处理者约束。后来 WareHub 把面单用于自营会员营销，且一次系统漏洞导致 3 万条地址泄露，双方互相说"是对方决定的 / 是对方系统的问题"，监管问询时拿不出任何书面依据。

✓ 建议写法（把边界锁死）

"就 NG-2026-017 履约所需个人信息，甲方为控制者、乙方为受托处理方；双方另签 DPA（Data Processing Agreement，数据处理协议），覆盖目的、期限、子处理者、安全措施、权利协助、审计、删除返还、跨境机制八要件。乙方仅按甲方书面指示处理；超出白名单字段须事先同意；事件 24 小时内书面通知；合同终止后 X 个工作日内删除并出具证明。"

大白话：差别就在"身份 + DPA + 边界"三件事写没写：没写，数据出国像没护照；写了，每一份数据都有"护送函"和"归期"。

就好比：接接口前先过这八问，等于发车前检查油、电、胎、证——少查一项，半路抛锚的代价远大于五分钟。

八、本页 Checklist：系统对接前八问

  • 传什么？逐字段盘点面单/轨迹/签收/画像/售后，标注"直接/间接识别"与"是否必需"，形成《数据出境清单》。
  • 走哪条出境路径？依现行《个人信息保护法》及《促进和规范数据跨境流动规定》判定适用安全评估 / 标准合同备案 / 豁免，以最新规定为准。
  • 谁控制、谁处理？在主协议首句写清：霓光为控制者、WareHub 为受托处理方；WareHub 另定用途时须另行取得合法基础。
  • DPA 签了没？与 WareHub 签署覆盖八要件的 DPA，缺失项以附件补齐，附件优先于模板。
  • 最小化做到没？面单只传履约必需字段；非必需字段（会员等级等）境内去标识化后传代码，不传原始值。
  • 留多久？明确面单/轨迹/签收/画像的删除或匿名化周期，写入 DPA，与日志留存分开约定。
  • 技术与合同咬合没？API 最小权限、TLS 加密、全量日志、访问控制、事件 24 小时通知——写进接口附件与 DPA。
  • 应急有预案没？泄露/丢失的通报路径、记录台账、对外依法通报责任归属，事先演练一遍。
