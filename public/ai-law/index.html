脱敏声明（先读这一条）

本文件全篇不出现集团真实商号、门店具名、供应商名称、租金与抽成比例、毛利数据，一律以「集团 / H 集团」「A 类门店」「供应商 S」等代号表述。原因是本文件拟对外发布（个人网站 / 行业交流），而珠宝零售的租金条款、抽成比例、采购价格属核心商业秘密，披露即构成竞争损害。

内部落地版请另建一份未脱敏副本，按第 06 章权限矩阵管控，两份文件不得混用。

这份方案的方法论立场

市面上讲「企业法律 AI」的材料，九成在讲模型多强、RAG 多先进。但法务 AI 项目失败的真正原因从来不是模型——是三件事：场景选错（做了没人用的东西）、语料没整理（垃圾进垃圾出）、没有引用溯源（编了一条不存在的法条，从此再没人敢用）。

所以本方案的重心分配是：场景与数据 60%、合规与治理 20%、技术选型 15%、模型 5%。模型是最不值得纠结的一环。

◆ 判断一：不要自研

2026 年的开源生态已经成熟到「法务部 + 1 名 IT」就能搭出生产级系统。自研 RAG 是浪费预算。选 Apache-2.0 / MIT 栈，站在社区肩膀上。

◆ 判断二：不要上法律垂类模型

中文法律垂类模型普遍停更、License 带非商用限制（ChatLaw 是 AGPL-3.0，HanFei / Lawyer-LLaMA 明确禁商用），且能力已被 Qwen3、DeepSeek 等通用强基座反超。强通用基座 + 私域语料 + 强制引用是更优解。

◆ 判断三：先做「不性感」的场景

租赁合同审查、法规问答、投诉话术——这些不酷，但占了法务部 70% 的工时。先打穿它们拿到可信度，再谈智能体。

1.3 珠宝零售特有的四个「坑」

通用企业法律 AI 方案不会覆盖这些，但它们是珠宝行业的高频雷区，必须在知识库里专门建库：

① 贵金属纯度与命名的强制标准

首饰的纯度标识、命名方法、印记受强制性国家标准约束（GB 11887 系列，具体版本须核实）。命名错一个字——例如把「足金」标成「千足金」、把「合成」写成「天然」——就是《产品质量法》与《消法》下的欺诈风险，客诉高发。

AI 用途：门店上架标签 / 详情页文案批量合规预检。

② 「三包」误区

珠宝首饰通常不在国家《部分商品修理更换退货责任规定》的目录内（该目录以家电、摩托车等为主）。所以「7 天无理由」不等于「珠宝适用」，但电商渠道又受《电子商务法》与平台规则约束，线下则靠企业自定承诺。

AI 用途：按渠道（线下 / 电商 / 直播 / 境外）给出差异化的退换货口径，避免门店乱承诺。

③ 大额现金与反洗钱（双法域）

珠宝是典型的现金高发行业。内地《反洗钱法》项下特定非金融机构义务范围、以及香港《打击洗钱及恐怖分子资金筹集条例》（第 615 章）下的贵金属及宝石交易商（DPMS）注册与尽职调查制度，构成两套并行要求。香港侧对现金交易的门槛与登记义务有明确规则（须核实现行门槛与最新修订）。

AI 用途：门店大额现金交易 SOP 问答 + 尽调留痕清单生成。

④ 门店人脸采集与会员数据出境

门店客流分析用的人脸采集，在内地属敏感个人信息，PIPL 项下须单独同意且须有必要性论证；会员数据回传香港总部则触发数据出境合规路径（PIPL 第 38 条）。香港侧 PDPO 虽无出境限制，但六项保障资料原则仍适用。

AI 用途：新店 / 新系统上线前的合规 checklist 自动生成。这也是本项目自身必须先过关的一关（第 07 章）。

02目标与红线边界

在谈技术之前，先把「能做什么、绝不能做什么」写死。这份边界清单的价值高于任何技术方案——它决定了这个项目会不会在某个时刻被一个幻觉法条毁掉。

2.1 系统定位：一句话

本系统是「法务部内部的检索增强起草与初筛工具」，不是自动律师、不是法律意见生成器、不对任何人直接输出终局结论。
它的全部产出，法律性质上是「助理起草的草稿」，必须经法务人员复核签字后方可对外。

2.2 六条红线（写入系统提示词 + 员工手册）

#红线具体规则与技术实现

为什么 P0 选「法规问答」而不是「合同审查」？

因为合同审查的验收成本高——需要法务逐份比对，一轮回测就是几天。而法规问答可以立刻用 50 道题测出引用准确率，一周内就能给老板看到「这个东西靠不靠谱」。

先用低验收成本的场景建立信任与使用权，再攻高价值场景。顺序反了，项目会死在第一个场景上——因为合同审查做得不够好时，法务会直接判定「AI 不行」，而法规问答做得不够好时，大家只会说「还得再调调」。

3.1 场景卡：门店租约审查（P0 主打，展开说明）

这是投入产出比最高的场景，值得单独设计。一份典型商场珠宝专柜租赁合同的审查，本质是「把这份合同和公司的谈判底线逐条对齐」，而不是从零做法律判断。

输入
  • 合同 PDF（扫描件 / 电子版，30–60 页）
  • 门店类型（商场专柜 / 街铺 / 购物中心）、面积、区域
  • 本次是新签 / 续签 / 变更（规则不同）
规则卡（法务部先写出来，这是核心资产）
  • 租金与物业管理费：构成、涨幅上限、是否含税
  • 抽成租金：基数口径（含税/不含税、是否扣退换货）、保底 vs 抽成取高
  • 免租期 / 装修期：天数、起算点、是否免物业与推广费
  • 保证金：金额、退还条件与时限、可否抵扣欠租
  • 续租与优先承租权、转租与分租
  • 提前解约：通知期、违约金、装修残值补偿
  • 商场统一收银：结算账期、对账、扣点
  • 装修与消防责任、恢复原状义务
  • 商场闭店 / 业态调整时的补偿
  • 不可抗力与情势变更、停业损失分担
输出模板（三件套）
  1. 风险分级表：每个条款一行，标注红（不可接受）/ 黄（需谈判）/ 绿（可接受）+ 理由 + 依据（公司底线第 N 条 / 法条）。
  2. 修订建议稿：直接给出可替换的条款文字，法务复制粘贴即可，不用重新措辞。
  3. 缺失条款提醒：标准范本里有、这份合同里没有的条款（常见于商场强势格式合同）。
关键前提：先有「谈判底线清单」

如果公司没有一份成文的租赁谈判底线，这个场景做不出来。AI 没法凭空知道你们能接受多少天免租期。
所以 W3–W4 的第一件事不是装系统，是法务部坐下来把这张表写出来。这件事本身就有巨大价值——它把老师傅脑子里的经验变成了组织资产，而且这份表在未来几年都会持续有用，即使 AI 项目失败也不亏。

4.1 一条查询的完整生命周期（以门店提问为例）

  1. 输入：店长在企业微信问「顾客买了 3 天的钻戒，吊牌没拆，要求退货，能退吗？」
  2. 路由：编排层识别为「消费者纠纷 + 退换货 + 线下渠道」，选择对应 prompt 与语料集合（消法 + 电商法 + 公司退换货 SOP）
  3. 检索：向量召回 Top 20 → BM25 补充 → RRF 融合 → Rerank 精排到 Top 5
  4. 生成：本地模型基于 Top 5 生成，强制每条结论标注来源编号
  5. 护栏：校验引用是否真实存在于检索结果（正则抽取条号 + 比对原文）→ 无引用或匹配失败则触发拒答或转人工
  6. 输出：结论 + 依据（可点开原文）+ 操作要点 + 「如涉以下情形请转法务」（金额超阈值 / 顾客已投诉 / 媒体介入）
  7. 留痕：问答全链路日志（提问人、时间、命中语料、模型版本、最终答复），用于审计与后续评测

5.3 选型踩坑清单

  • Dify 多租户条款：若未来想给集团旗下其他品牌 / 关联公司各开一个工作区，可能触发 License 限制。立项时就要确定是「单一 workspace + 权限分组」还是采购商业授权。
  • RAGFlow 资源占用：内置 embedding 模型 + DeepDoc OCR 对内存与算力要求高，官方建议 16GB+ 内存，OCR 密集场景建议 GPU。别在 8GB 内存的旧服务器上试。
  • MinerU 的自定义 License：79.9k star 很诱人，但 License 写的是 NOASSERTION（非标准），不能默认当 Apache 用。要用就先做一次书面 License 审阅，留档。
  • 模型升级破坏效果：基座模型小版本更新可能改变输出风格、打断已有的 prompt 与输出解析。版本必须锁死，升级走变更流程 + 黄金集回归。
  • 繁体处理：香港法例与港方合同为繁体。检索侧建议保留原文繁体（不要强行转简），生成侧在 prompt 中按用户所在法域指定输出语种。

06知识库建设：这个项目 60% 的工作量在这里

如果只记住这份文件的一页，记这页。所有 RAG 项目的成败，分水岭都在语料。模型可以换、框架可以换，语料没建好就是垃圾进垃圾出，而且会以「AI 编了个不存在的法条」这种最致命的方式失败。

6.1 语料四层模型

L1 外部法规与标准

谁都能看，优先建。内地法律法规 + 部门规章 + 强制性国家标准；香港法例与附属法例。

  • 特点：公开、结构化、有明确版本与生效日期
  • 风险：版本过时。必须带「生效日期 + 效力状态 + 来源 URL」
  • 规模预估：300–800 部，10 万级条目
L2 公司制度与范本

核心价值所在，也是 AI 能不能「说公司的话」的关键。

  • 标准租赁合同范本 + 谈判底线清单、供应商框架协议范本
  • 门店运营 SOP、商品标识规范、退换货政策、投诉处理指引
  • 员工手册、劳动合同范本、授权审批权限表
  • 特点：内部、权威、需要版本管理
L3 历史合同与审查意见（涉密）

最脏也最值钱。法务过往在合同上写的批注，本质是「公司风险偏好的真实标注数据」。

  • 200+ 份已签租约（入库前必须脱敏：房东主体、租金金额、抽成比例）
  • 历史审查意见与批注
  • 争议与诉讼材料（单独最高权限，建议不进向量库，只做受控检索）
  • 风险：涉密泄露。默认只存脱敏摘要 + 条款级片段，原文不出权限边界
L4 案例与 FAQ 沉淀

让系统越用越聪明的一层。

  • 法务部 FAQ：把重复回答过的问题整理成标准问答对
  • 监管动态与处罚案例（同行被罚的公开案例，警示价值极高）
  • 系统上线后的「人工修正记录」：AI 答错了、法务改了什么 → 回流成语料

6.4 分块策略（按文档类型分别设计）

法规 / 标准

一条（款）一个 chunk，绝不跨条切分。每条 chunk 头部注入上下文标头：《XX法》第N条 | 生效日期 | 效力状态。

  • 理由：法条引用必须精确到条，跨条切会导致引用指向错误的条文
合同 / 协议

按条款编号切分（第 X 条一段），保留「合同类型 + 当事人类别 + 签署年份 + 区域」元数据。长条款按款再分，但标头保留条号。

  • 理由：审查场景需要「这份合同第 8 条 vs 底线第 8 条」的对齐
公司制度 / SOP

按章节切分，chunk 头部注入「制度名 + 章节路径 + 版本日期」。

  • 理由：制度问答常问「XX 流程怎么走」，需要完整章节上下文
FAQ / 案例

一条问答一个 chunk（Q 与 A 不分开），带场景标签。

  • 理由：语义相似度最高，是最容易被正确召回的一类
一条硬性禁令

禁止跨文档合并切块。把 A 合同和 B 合同拼进同一个 chunk，会导致检索命中 A 却引用了 B 的条款——这是法务 AI 最危险的一类错误，因为它看起来完全合理，引用也「有」，但指向的是另一份文件。

6.5 更新机制：法条会变，知识库不能睡着

  • 变更监控：对国家法律法规数据库、香港 data.gov.hk 法例数据集设置定期（建议每周）比对，发现版本变化自动通知法务部。
  • 失效标注：法条修订后，旧版本不删除，但标记为「已废止 / 已被修订」，检索时默认过滤，避免 AI 引用失效条文。
  • 复核节奏：L1 每季度全量核验一次效力状态；L2 随制度修订同步更新；L3 每半年评估是否继续保留。
  • 责任人：明确到人（建议法务专员 + IT 各一名），写进岗位说明书。没责任人的知识库，半年后就烂了。

07双法域合规与风控：法务部自己先过关

这一章是法务总监的「自证清白」章节。我们做的是法律 AI，如果它自己不合规，那不只是项目失败，是职业风险。以下每一项都应在立项前形成书面结论并留档。

7.1 内地侧合规判断

关键判断：这是「内部工具」，不是「生成式 AI 服务」

《生成式人工智能服务管理暂行办法》（2023-08-15 施行）规制的是向境内公众提供生成式 AI 服务的情形。本系统仅面向公司内部员工（法务部、门店）开放，不向社会公众提供，因此通常不构成该办法项下的「生成式 AI 服务提供者」，一般无需履行备案与安全评估程序。

但这个结论有三个前提，任一不成立即需重新评估：① 系统不对外（顾客、供应商、公众）开放；② 不嵌入对外产品（如面向消费者的智能客服）；③ 不生成对外发布的内容。若未来要上线「顾客-facing 的法律问答机器人」，合规义务完全不同，须单独评估。

提示：此判断属法律判断，建议以书面形式报备并留存，必要时咨询外部律师确认。切勿默认成立。

7.3 数据出境：本项目最容易踩雷的地方

问题本质

集团总部在香港，内地 200+ 门店的合同、会员、员工数据如果统一回传香港服务器，构成 PIPL 第 38 条项下的数据出境，需走安全评估 / 标准合同 / 认证三条路径之一。对内部 AI 系统而言，这是一笔不必要的合规成本与风险。

架构解法：双区部署，数据不出境。

REGION A
内地
部署：RAGFlow + Dify + 本地模型，部署在内地机房 / 内网
数据：内地门店合同、内地法规、内地员工与顾客数据（脱敏后）
用户：内地法务、内地门店店长、区域经理
红线：原始合同与个人信息不出境
▲ 仅脱敏统计指标 / 知识条目摘要，且须经法务审批 ▲
REGION B
香港
部署：独立实例，香港服务器
数据：香港法例、香港门店合同、集团层面制度（不含内地个人信息）
用户：香港总部法务、香港门店

两侧共享的只有不含个人信息的法律知识点（例如「某类条款的风险提示」「法条释义」），且共享前经法务审批。这样既保证了「香港总部能沉淀方法论」，又避免了大规模数据出境的合规负担。

7.4 执业边界与免责

  • 系统名称不要叫「AI 律师」，叫「法务助手 / 法务知识库」。名称会影响使用者对其产出的信任度定位。
  • 免责声明模板（每次输出自动追加）：「本答复由 AI 基于内部知识库生成，为助理级初稿，未经法务复核不构成法律意见，不得直接对外使用。涉及具体权利义务的判断，请转法务部确认。」
  • 使用者告知：上线前对门店与区域经理做一次培训，明确「AI 给的是口径，不是授权」。特别是赔偿金额、对外承诺，仍需走既有审批。
  • 责任归属：写入员工手册——使用 AI 不减免使用人的注意义务，因未复核导致的后果由使用人与复核人承担。

W5 的黄金测试集必须在系统调优之前，而不是之后。很多团队先调系统、调到最后才想起「怎么证明它变好了」，结果只能凭感觉。先出题、后调优，才有客观基线。

10评测与度量：让系统不腐坏

没有评测的 AI 系统，三个月后就会悄悄变差——语料更新了、prompt 改了、模型升了，没人知道效果怎么样了。评测体系是这个项目的保险丝。

10.1 黄金测试集（Golden Set）

怎么出题
  • 来源必须是真实问题：从过去一年的工单、企微咨询记录里挑，不是拍脑袋编。
  • 每题三部分：问题 + 标准答案要点 + 应命中的正确依据（法规第几条 / 制度第几章）。第三部分最关键——它让「引用对不对」变得可自动判定。
  • 覆盖分布：按第 01 章工作量分布配比，高频场景多出题。
  • 必须包含「陷阱题」：10% 的题目是知识库里没有答案的，用来测试系统会不会老实说「不知道」。系统敢不敢拒答，比它答对多少更重要。
  • 规模：v1 出 50 题（W5），S2 扩到 100 题，稳定后 150–200 题。
  • 禁止 AI 出题：让模型自己生成测试题，等于让它自己出考卷自己判分。

10.2 核心指标

指标目标值怎么测为什么是它
引用准确率≥95%抽取回答中的引用编号 → 与知识库原文比对是否存在且内容一致第一指标。引用错了，一切免谈

10.3 回归评测流水线（W21 建）

  1. 触发条件：语料批量更新、prompt 修改、模型版本升级、RAG 参数调整——任一发生即触发。
  2. 自动执行：跑完整黄金集 → 计算全部指标 → 与基线对比。
  3. 熔断规则：引用准确率或幻觉率跌破阈值 → 自动阻断上线 + 通知法务负责人。
  4. 人工抽检：每月法务人工抽 20 条真实问答，检查「自动化指标看不出来的问题」（比如语气、口径与公司文化不符）。
  5. 回流机制：人工修正过的答案 → 进入 L4 语料 → 下次遇到同类问题答对。这是系统越用越聪明的唯一路径。

12第一周就能做的 5 件事（不等预算）

这五件事不需要任何预算、不需要 IT 配合、不需要老板批，本周就能全部做完。做完之后，你会对这个项目能不能成有完全不同的判断。

① 拉全年法务工单统计（半天）

从 OA、邮箱、企微导出过去 12 个月全部法务请求，按业务域分桶计数。产出一张饼图。

为什么先做这个：它会直接告诉你第 01 章的估算表对不对。如果你们家的工单分布和估算差很远（比如租赁只占 8%），整个场景优先级都要重排。用数据替代直觉，这是这个项目里最值钱的半天。

为什么先做这个：这一步通常会暴露一个残酷现实——「我们以为有的东西，其实找不到」。而且无论 AI 项目做不做，这个目录都有用。

③ 出黄金测试集前 30 题（1 天）

从工单里挑 30 个真实高频问题，每题写清标准答案要点 + 应命中依据。

为什么先做这个：未来所有「效果变好还是变差」的判断都靠它。先出题，后面才有基线。而且出题的过程会逼你厘清「这个场景到底要答成什么样才算对」。

④ 写六条红线，让全部门签字（半天）

把第 02 章的六条红线改成一页纸，部门内传阅确认。

为什么先做这个：规则要在系统之前确立，不是在系统出问题之后补。而且这份签字文件，是未来万一出事时证明「我们尽到了注意义务」的关键证据。

⑤ 写《租赁谈判底线清单》第一版（2 天）

10 类核心条款 × 每类的可接受区间 / 谈判目标 / 红线。先写个粗版，后面再迭代。

为什么先做这个：这是整份方案里唯一「纯法务产出、不依赖任何技术」的高价值资产。它把资深法务脑子里的经验变成组织资产。即使最后 AI 项目因为任何原因停了，这份清单本身也已经值回票价——新来的法务专员照着它就能审租约。
