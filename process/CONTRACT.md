# CONTRACT.md — 行为契约（写给接手本仓库的 AI）

> 这份文件管的是「**你怎么做事**」，不是「项目是什么」。
> - 项目是什么、现在挂了什么没解决 → 看 `README.md`
> - 换机器 / 换账号怎么用 → 看 `MIGRATION.md`
> - 同一件事做完了 → 看 `03-问题台账/SOLVED.md`
>
> **你（AI）为什么读到这里**：`AGENTS.md` 把你送到这里。你接手了这个仓库，下面这些是约定，不是建议。

---

## 零、一句话

这个仓库有个 `process/` 档案库，记着这个项目**做出来的每一步和为什么**。
你每干一天活，就往里面加一天。**不做这件事，档案库三个月就腐烂成流水账，换人接手就只能靠猜。**

## 一、开工清单（每次会话开始，30 秒内）

1. **读 `README.md`** —— 入口，它告诉你现在挂了什么没解决、哪些决定不要推翻。
2. **读 `03-问题台账/OPEN.md`** —— 开工前先看有没有轮到你认领的条目。按下表判断归不归你：

   | 条目的样子 | 判断 |
   |---|---|
   | 署名是 `Andy` / 写着「等他拍板」「等他点头」 | **不认领**，那是等他决定 |
   | 「下次第一步」需要他本人操作、外部权限、别的仓库才能动 | **不认领** |
   | 我能独立做完、但不需要他先做决定 | **认领**，做完在日志里写明 |
   | 拿不准 | **问一句再动**，别自己挑最难的 |

   **只有第 1、2 类要排除**，其余默认归我。不写这条，接手的人会在「这条到底归谁」上卡住然后凭感觉挑。**2026-09-27 实测**：新 AI 靠排除法从六条里挑出 #04，判据对了，但它是逐条排除才推出来的——慢，而且下次换个场景就会漏。
3. **看一眼「今日索引」的最新一行** —— 确认上一班的人干到哪了，别重复劳动。
4. **要动 `src/` 或发布相关文件 → 先读 `01-项目现状/workflows.md`**。八条红线在动手前必读（本地禁 `npm run build`、只改中文源目录、改完 grep 核对……）。**只读前三步就改代码，等于对红线一无所知。**

> 如果日期是新的（没有今天这条）→ 你就是这一天第一个开工的，收工那节对你的权重最高。

## 二、收工六件事（做完才能说「做完了」）

按顺序来，除非某条确实无事可记：

| # | 动作 | 什么时候做 |
|---|---|---|
| 0 | **`npm run theme:check`** —— 子站的暗黑配色不写在 `style.css`，是四个补丁块塞在 HTML 里；补丁由 `scripts/apply-theme-kit.py` 接管。跑过任何 `sync:*`（rsync 会连带把块抹掉）就必须跑这条，退出码非 0 = 有站没补上 | 跑过任何 `sync:*` / 动过子站 HTML |
| 1 | **写 `04-每日日志/{今天}.md`** —— 照 `_templates/每日日志.md` 的格式。**文件已存在就在末尾追加，禁止覆盖** | 只要今天动过这个仓库的文件 |
| 2 | **更新 `README.md` 的「今日索引」** —— 加一行，别删表头 | 只要新增或改了档案库里的文件 |
| 3 | **提台账** —— 新卡住的开 OPEN 条目（写全四要素）；解决了的挪进 SOLVED，编号连着来 | 有真问题 |
| 4 | **新决定进 `02-决策日志/`** —— 只记不可逆的 | 你推翻或重定了某个做法 |
| 5 | **`git commit`** —— 档案库和代码一起走。**不用手动 push**：hook 已装上，提交后会自动 rebase 到线上最新并推上去（见第四节第一条） | 见第四节 |
| 6 | **验线上 + 验推送** —— 动过 `src/` 或任何子站，收工前**必须跑一条命令**，别自己拼 curl：

  ```bash
  bash scripts/verify-online.sh <slug或完整URL> "这次改动的关键文本" --wait 120   # 退出码非 0 = 没生效
  bash scripts/verify-online.sh --push                                            # 本地 HEAD 与 origin/main 对不上 = 推送静默失败
  ```

  GH Pages 有 10 分钟缓存，所以带 `--wait` 重试到刷出来为止。**只 grep 字符串会误判成功**（能命中文案常量，导航未必渲染），
  要查导航这类改动就传导航数组的判别串。网络不通时脚本会明说「没验成」，此时**不许写成「已上线」**。
  原理见 `01-项目现状/workflows.md` 第三节，排查顺序见第七节 | 动过会发布的东西 / 每次收工 |

**第 5 步可以跳过**（网络不通、凭据没配）。**第 6 步只在动过会发布的东西时才做**——
纯改 `process/` 档案库不用验线上。**其余四步跳过一次，档案库就少一天。**

> **第 6 步为什么从「写句话提醒」升级成「一条命令」**：2026-09-27 当天，这句话在契约里、在开场白里都写着，
> 但它的执行靠的是「记得」——和 hook 之前那次一样，写在文档里的规定动作，只在你想起它的时候才存在。
> 于是把 `workflows.md` 第三节那三步 curl 收成一个 `scripts/verify-online.sh`：
> **能带 --wait 等 GH Pages 刷出来、退出码能串链、网络不通会明说「没验成」而不是谎报「内容缺失」。**
> 规矩不变，但从「靠记性」变成「靠敲一行」。

> **半途打包（换电脑 / 长时间中断）不是这里的事**，那是事件驱动的，见第七节。日常收工只做上面五件。

## 三、写日志的格式（照抄，别自由发挥）

**五段式**，缺哪段写「无」，别删标题：

```
# 2026-09-28 · 周一
> 一句话总结今天。
## 做了什么        3-5 条，每条一行，别写成段落
## 问题            新开 #20、解决 #14（引编号）
## 今日决策         一行；有线就进 02-决策日志
## ⚖️ 小律的补充     风险 / 保留意见 / 如果重来会怎么做（不许空）
## 有意思的         非显然的发现（没有就写「无」）
```

- **当天已有日志时追加，不覆盖。** 在文件末尾加一段 `## 追加（当天下午）`，把上面的五段重复一遍。**覆盖等于销毁当天全部记录**——2026-09-27 那天的日志就被分了三个时段追加，就是因为同一天多件事。
- **编号规则**：问题用全局递增的 `#20`、`#21`（跨文件唯一），当前已用到 #19（见 `OPEN.md` / `SOLVED.md` 顶部）。分配前先查重。
- **OPEN 条目必须写全四件事**：现象 / 卡在哪 / 谁该动 / **下次第一步做什么**。少了最后一条，三个月后就是一堆没人认领的待办。
- **日期不凭记忆写**。复盘、日志里的日期一律 `git log --format="%h %ad %s" --date=short` 核对。本仓库已经栽过一次：凭记忆把 09-24 写成 09-23。
- **改完别信编辑工具的回执**。`Edit` 报「成功」没落盘过三次，写完必须 `grep` 核对关键内容。同一个病根：信记忆、信回执、不验结果。

## 四、git 同步规则

- **档案库和代码一起 commit**，不分开推。分开推的后果是换机器时档案库落后几个版本。
- **自动同步已经接管了 pull / push，靠的是 hook，不靠记。** 2026-09-27 起本仓库装了 `scripts/install-git-hooks.sh`：
  - 进入仓库 / 切换分支 → 自动把线上最新拉下来；
  - 提交之后 → 先 rebase 到最新，再自动推上去；
  - 推 `main` 前会警告一次（**这个仓库推 main 等于发布上线**，做了一半的东西先开 `wip/YYYYMMDD`）。
  - 所以收工动作里的第 5 条只需 `git commit`。**别再手写 `git push`**——会和 hook 打架，还会漏掉自动 rebase。
  - 换机器 / 新 clone 之后要重新安装一次：``bash scripts/install-git-hooks.sh``（卸载：`--uninstall`；只自动拉不自动推：`export AUTOSYNC_PUSH=0` 后重装）。
  - **不要擅自把 pull 挪到 `pre-commit`**。改动还挂在 index 上时 rebase 会把正在提交的这批搅散（实测提交被吞、改动掉回工作区）。这是踩过的坑，别重来。
- **接任务动手前，先显式 `git pull --rebase` 对齐一次（兜底）。** 自动同步 hook 在进目录 / 切分支时会拉，但**沙箱里 hook 未必触发**——只信它，会基于过期代码改，并发会话还可能让本地改动被回退（`#18` 同款代价）。所以每次接活、**读 `src/` / 改文件之前先拉一次**，确认 `origin/main` 已合并进本地。这条和「push 前再 rebase」是两段、不冲突：**动手前对齐、推送前再对齐**；前者防「基于旧代码改」，后者防「并发会话回退」。
- **push 之前先 `git pull --rebase`**（换机器后的第一次更重要）。`workflows.md` 红线 8 与本节是同一条，以本句为准。**不要只看「直接 push」的说法**——并发会话会回退已提交的编辑，跳这一步的代价见 `#18`。
- **push 不通先排查再求助**，顺序：`HTTP/1.1` → `userAgent` → 代理 → 网络。完整排障在 `MIGRATION.md` 第三节，别自己瞎试半小时。**四种根因里有一种是本地代理挂了**，判定命令写在那里。
- **`.gitignore` 只排构建产物**。往里面加东西之前想清楚：这东西换台机器还会需要吗？
- **凭据、token 一律不进仓库**，只记「在哪儿」。

## 五、禁止清单

1. **不要往 `.workbuddy/memory/` 写日志。** 该目录已被 `.gitignore` 排除，写进去等于没写，而且会和 `04-每日日志/` 分叉成两份。日志只进 `04-每日日志/`。
2. **不要在别处再造一份索引。** README 是唯一入口，单向引用。多个索引 = 必然腐烂。
3. **不要把结论写进行程。** `01-项目现状/` 只记此刻是什么样，会变的结论往上提到 README / 决策日志，过程留在日志。
4. **不要推翻没看过的决定。** 改配色、折叠交互、字体、动效前必读 `02-决策日志/`。`DECISIONS.md` 里明写「改色前先读」的就是这种。
5. **不要把案件材料、客户合同塞进来。** 保密边界见 `AGENTS.md`，这是这个仓库的私域范围。
6. **不要写「以后可能会用到」的文件。** 档案库死于无差别收集。

四项全过才算健康：

| 检查项 | 不健康长什么样 | 修法 |

## 七、半途打包（换电脑 / 中断前做，日常收工不做）

做了一半的功能，**git 带得走代码，带不走「我干到哪了、下一步是什么」**。半途换机器丢的正是后者，而且当时不知道自己丢了。打包分两步，缺一不可：

**第一步 · 状态写成文字** → 更新 `process/HANDOFF.md` 的前五节（第三节打勾、第四节写「下一步第一步」到能直接开干的粒度）。

**第二步 · 代码推上去**，且**只能推 wip 分支**（脚本命令 + 下面四行）：

```bash
python3 scripts/wip-snapshot.py                 # 生成 HANDOFF 第七节现场快照（分支/HEAD/未提交改动）
git checkout -b wip/$(date +%Y%m%d)             # 从 main 开一条，别动 main
git add -A
git commit -m "wip: <一句话描述在做什么>"
git push -u origin wip/$(date +%Y%m%d)
```

- **绝不推 main。** 本仓库 `.github/workflows/deploy.yml` 配的是 `on: push: branches: [main]`，推上去就触发构建，并把半成品发布到 **linqiongni.top**。这是唯一一条会伤到线上用户的红线。
- **用 commit，不用 `git stash`。** stash 推不到远端，换机器就没了。commit 是唯一能送出去的「未完工」形态；新机器上 `git reset --soft HEAD~1` 可原样拆回工作区。
- **现场快照别手改**，`wip-snapshot.py` 下次运行会覆盖第七节。
- **快照会过期。** 第七节记的是抓那一刻的样子，越久越不可信——**push 前重跑一次** `python3 scripts/wip-snapshot.py`。
- **前三节没填，脚本会直接拒绝生成快照**（退码 2）。实测里新 AI 说过一句话很准：跳过填卡、照跑后面四行，什么也拦不住。
- 结束这项活之后，把 `HANDOFF.md` 清空重写，别让它和后续主题混在一起。

## 八、这份契约怎么改

- 有你不认同的规则：**先照做，再提意见**。口头提，别偷偷不执行。
- 连续三次想改同一条 → 写进 `05-想法池/ideas.md`，等 Andy 点头再改本文件。
- **改完在文件末尾「版本记录」加一行**，写清改了什么、为什么。契约没有版本记录就等于没有约束。
