**关于今天这个档案库本身，我有保留意见，直说：**

把它做成"过程档案"容易，做成"能被接手的东西"难。区别在于——**没人维护的档案库活不过两周**。今天填进去的内容全是 2026-09-27 的快照，两周后如果没人更新，`process/` 就会变成第二个 `MEMORY.md`：**看起来齐全，读起来过时，比没有更糟**，因为你会信它。

## 有意思的

1. **同一个 `git status`，AI 跑 exit 0，用户跑报权限错。** 第一反应是"AI 有特权"，实际是执行者身份不同：Bash 跑在 WorkBuddy 宿主进程里、被授予了这些目录的访问权，而用户的常规终端受系统 TCC 管控。**排查"本机奇怪的报错"时，先确认"这个报错是谁在执行"，能省掉一半的弯路。**
2. **"我调小了参数但没变化"——先查阻尼。** 鱼影那次把速度上限压到 1/2.5 完全没用，因为缺阻尼时速度几帧就顶到上限；加了 `DAMP=0.95` 之后稳态速度 ≈ 力/(1−阻尼) 才可被调节。**这条是通用的：任何"我压了上限但没反应"的反馈问题，根因几乎都在积分器缺阻尼。**

**⚖️ 小律的补充**

这次补的东西，本质上是一个我在上一轮偷过的懒被 Andy 逼出来的代价。

上一轮我做了 16 个文件、跑了冷启动测试、按反馈改到"合格"，然后停下来交付。**但那个测试从头到尾考的是「档案库里有没有答案」，没考「接手的人会不会维护它」。** 一个有完善内容、却没人更新的档案库，比没有更糟——它会给你一种"有流程"的错觉。所以补的这两份文件，价值不在内容，在于把「维护」从**口头承诺变成可执行条款**。

还有个更直白的教训：**`AGENTS.md` 里原本一个字都没提 `process/`。** 一个接手的 AI 每次会话第一件事就是读它，它不提档案库，档案库等于不存在。我前面两轮做得再认真，在这条链上都是零。**做完内容不等于接得住——得验的是"新人能不能找到它"，不是"我写得好不好"。**

**有意思的**

- **"git 推不动"这个问题，症状只有一种，根因有三种。** 空 proxy 配置、UA 被拦、HTTP/2 被拒，都表现为 `git push` 报错而 `curl github.com` 正常。不按顺序查就会在同一个症状上反复试半小时——**"症状相同 ≠ 根因相同"，排障必须走 checklist，不能靠直觉。**
- **验证"换机器能不能接住"，只能靠冷启动测试**，没法靠检查文件数量。`process/` 这次 push 之后，换机器的人 `git clone` 就全有了；但如果他不知道要先读 `CONTRACT.md`，他照样不会维护。所以 MIGRATION 里把验收写成**强制动作**：新机器跑一次冷启动，答不出四个问题就补 README。

**⚖️ 小律的补充**

这两件事其实是同一个毛病在两个层面发作：

**一是机制层面。** 我上一轮把「记进用户级记忆」当成了「以后会自动生效」，其实不是。记忆是静态文本，注入给我只是让我"看见"，没有一条机制保证我在新项目开工时照它做。**Andy 问「那我新项目会自动生成吗」，答案是不会——这个提问当场就把我一个偷懒的假设戳破了。**

补救办法是开技能：技能有触发词，说「建一套」就会被触发执行，比记忆可靠一个量级。**这跟"写进文档"和"写成可执行程序"的区别是一回事。**

**二是排障层面。** 写 MIGRATION 排障表时，我凭记忆只写了三种根因（空 proxy 配置 / UA 被拦 / HTTP2 被拒）——**结果当天就撞上第四种（代理挂了），多绕了一圈。** 排障表凭记忆写，等于把自己踩过的坑重写一遍还漏掉最新的那个。**这类清单必须写实测案例，不能写论文。**

**有意思的**

- **「症状相同 ≠ 根因相同，也 ≠ 根因只有一个。」** git push 失败这一条，本仓库踩过四个不同的坑。经验的可复用前提是**排成 checklist**，散落在记忆里的经验只会让人凭直觉重试——而直觉在这种情况下的命中率约等于零。

**⚖️ 小律的补充**

风险：定时任务目前只做检查不自动补写，省事但依赖「有人理」；如果连续几天没动静，它会安静地什么都不做，至少不会制造假记录。真正的隐患是**我这次修的是「换机器场景」，而换机器本身还没发生**——没实证的场景改的东西最容易被想当然带偏，下次有机会在新机器上再跑一次冷启动验收。

**有意思的**

- **「契约写得越像命令，越容易在细节上出错。」** 三份文件都在强调「必须 push」「必须写日志」，但毁数据的恰恰是一句最平常的「写 `04-每日日志/今天.md`」——它默认了「今天还没有」。**约束的空白处不在大动作上，在动词的宾语上。**
