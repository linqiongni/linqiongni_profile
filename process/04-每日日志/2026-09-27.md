## 追加（当天下午，第六件事）· 半途打包机制

Andy 问：「开发一半的功能，怎么让它把当前状态、思路都打包上去 git，换个电脑能继续干。」

**先查出一个会伤到线上的事实**：`.github/workflows/deploy.yml` 是 `on: push: branches: [main]`。**半成品推 main 会触发构建，并发到 linqiongni.top。** 所以「怎么打包」的答案里，有一条是「只能推 wip 分支」。这条以前没人提过，踩上去就是拿线上用户试错。

配套两样新东西：`process/HANDOFF.md`（断点卡，七节，含与 OPEN 台账 / 每日日志的边界表）和 `scripts/wip-snapshot.py`（现场快照：分支 / HEAD / 未提交改动 / 今天动过哪些文件）。

**第四次实测（新 AI 走打包流程）的评语很值钱**：

- **「卡的不是流程是纪律。」** 规则写得再清楚，「先把前三节填满」这一步没有任何校验，跳过也照样能跑完后面四行。
- **「机制假定上一个人一定会更新文档，而这恰恰是最容易松的那一环。」**
- 它自己发现了一个文档里没人写的东西：本地两条 stash（`stash@{0}` 含 2026-09-17 的日志、`stash@{1} wip-MEMORY`）和一条从未 push 的分支 `save-visual-f276c11`——**换机器就永久消失**，其中那份日志可能还是唯一的。已开台账 **#20** 等 Andy 定。

据此修三处：① 脚本加前置校验——前三节还是空占位符就**拒绝生成快照**（已两种情形实测：空卡拒、已填放行）；② `HANDOFF.md` 前五节填成真实状态，消掉「卡里写着没在做事、磁盘上一堆未提交改动」的不一致；③ 修正 `CONTRACT.md` 第七节「四行」与实际对不上，补「快照会过期、push 前重跑」。

如果重来：**凡是靠人自觉的环节，都要配一道机器校验。** 前四轮我们一直在写「应该怎么做」，这一轮才第一次写「不这么做会怎样」——后者才拦得住。

## 追加（当天下午，第七件事）· 打包压成一条命令，并实跑一次

**当场实跑，把这套机制自己打包送出去**：推到 `wip/20260927` 三条提交（`8f6bc8a` 机制本体 / `2b9e417` 脚本缺陷修复 / `4d8b9f5` 收尾）。**main 仍是 `a4d7522`，线上没被碰过**——这算是把「只推 wip」这条红线亲手验了一遍。

1. **用 stdout 判 git 成败是错的。** 中文 locale 下 `git checkout -b` 成功也往 stderr 打 `create mode 100644 …`，`git commit` 成功时 stdout 是空串。结果把成功报成「建分支失败」，还把 `create mode …` 当成提交信息打印出来。**调 git 一律看返回码。**
2. **多块文本拼接用 `+` 会粘连。** 两份 `todo()` 返回值相加，末行变成 `- \`scripts/wip-pack.py\`_（无）_`。

## 追加（当天下午，第八件事）· 自动同步：开工自动拉、提交自动推

Andy 提了三条硬要求：**每次开发改代码前要同步 pull、保证线上的同步过来、每个电脑都要自动有这个操作、
功能实现后自动 push**。这三条的本质是「别靠人记」——那么唯一可靠的落点就是 **git hook**：绑在仓库上、
装一次常驻，clone 到新机器再装一次。

新增 `scripts/install-git-hooks.sh`（幂等，支持 `--uninstall` / 指定仓库路径 / `AUTOSYNC_PUSH=0` 只拉不推）。
装上后：`post-checkout` 进入仓库或切分支时自动拉；`post-commit` 提交后先 rebase 到最新再自动推；
`pre-push` 兜底再拉一次；推 `main` 前警告一次（**这个仓库推 main 等于发布上线**）。

**时序是本次最大的教训：`pre-commit` 里绝不能 pull。** 那一批改动还挂在 index 上，`--rebase` 会把
正在提交的这批搅散。实测结果：A2 提交根本没产生 commit，HEAD 直接快进到别人的提交，改动掉回工作区。
用户看到的就是「我提了一个功能，历史里没有它」。所有会动状态的动作一律改到 commit 之后。

隔离环境端到端测了四轮（临时裸仓库，不碰线上），抓到四个**不报错但功能哑火**的坑：
① macOS 没有 GNU `timeout`，探测静默失败 → 误判「远端是空仓库」→ 自动同步整体失效；
② `ls-remote --heads <remote> HEAD` 永远失败（HEAD 是符号引用，不匹配 `refs/heads/*`）；
③ 空远端 ≠ 断网，首次提交就得单独放行；④ 旧版本生成的 hook 不清理，会调被覆盖后的新 core 在危险位置执行。
外加两个语言层坑：UTF-8 下 bash 允许全角字符进变量名（`（$REPO）` 被当成变量名）、git 看返回码不看 stdout。

真实仓库上现场验了一次：另一会话推的 `5c0ce58` 被自动拉下来、我的提交 rebase 到它之上再自动推——
**唯一的缺口是当时网络 502，push 没打成**（curl 也是 000，属周期性网络故障，非 hook 问题）。

## 追加（当天下午，第八件事）· 新设备「一条命令装好」实测通过

Andy 明确场景了：**不是一次性换电脑，是两台设备来回用**；用户级记忆暂不同步（习惯两边用久了本来就一样）。
真正在意的是「换个设备时，自动 push/pull 能立马装上」。

于是把「装 hook」从一段说明压成一个自带自检的命令 `scripts/setup-device.sh`：装完当场验六项
（入口 hook 在 / 可执行 / 核心脚本语法 / 有 remote / 有上游 / 当前分支有上游），有一项不过就红字指出是哪一项。

**用一台真 clone 的新设备跑通了全流程**：clone（HEAD `ad1e7f2`、hook 目录为空）→ 一条命令装上 →
六项自检全绿 → 改一行真提交 → 自动拉、自动推、远端收到、推 main 的发布警告也正常打出。

两个真教训：
1. **「一键装配」脚本本身必须先 push 过，别人才 clone 得到。** 第一次拿"新设备"测时报
   `No such file or directory`——那个文件只是本地新建没提交。测新设备前先确认要装的东西已在远端，
   否则测的是一个不存在的设备。
2. **clone 之后 hook 不存在是绝对安静的**，不会有任何提示（clone 不跑第三方脚本）。
   「没装」和「装好了」在用户眼里长得一模一样。所以别指望 clone 会喊你装，只能在 core 缺失时提醒重跑。

顺带：同一条「UTF-8 下全角字符进变量名」的坑，下午连踩第三次（安装器 2 处 + 新写的自检脚本 1 处）。
已加静态自查命令写进技能：写完 shell 先 `grep -nE '\$[A-Za-z_][A-Za-z0-9_]*[），。、：；]' <脚本> | grep -v '${'`
扫一遍再 `bash -n`。

`process/MIGRATION.md` 改写为**多设备共用**场景（七版）：清单定成三件事——clone / 一条命令 / 贴开场白；
用户级记忆那节标注「暂不纳入同步」并写明理由与将来怎么启用。

### 追加（当天傍晚三轮）· 老设备同步：「直接 pull 一下」这个答案是错的

第一反应是「直接让它 pull 一下吗」。

**这个直觉漏了最关键的一条：hook 不进 git。** `git pull` 拉的是代码，`.git/hooks/` 里那些
自动拉/自动推的脚本拉不到，拉一百次那台机器还是没有自动同步。所以答案不是一句 pull，是三下：

`git status`（先看有没有没提交的改动）→ `git pull --rebase` → `bash scripts/setup-device.sh`。

第二个问题「他知道这些机制在哪吗」——**不知道，除非你说**。
那台电脑的 WorkBuddy 只知道仓库里有什么文件，不知道 `.git/hooks/` 里躺着自动同步、
不知道 pull 不能挪进 pre-commit、不知道推 main 等于把 linqiongni.top 发一遍。
所以还要给它一段话，把机制位置点名（这一句是「Tell it where the mechanism is」，不是客套）。

已在 `process/开场白.md` 加第三节写清这套流程 + 那段话术（三版）；并提醒了真实风险：
**那台电脑若当天也在动同一个仓库，两边改同一文件会冲突**——改动不会丢，按 `git add` +
`git rebase --continue` 处理；`stash` 一律先看清内容再 drop。

**方法论沉淀**：判断「某个东西能不能靠 pull 带过去」时，先问一句它是否属于
**git 会跟踪的内容**——代码、文档会；`.git/` 内部的 hook、本地配置、凭据不会。
Andy 的直觉默认是「同步 = pull」，而这类机制恰恰落在 pull 覆盖不到的那一侧。

而且「grep 字符串命中」会误判成功（命中文案常量，导航未必渲染）。现成命令早就躺在
`01-项目现状/workflows.md` 第三节，但它是"想起来才查"，不是收工清单里的一件。

`CONTRACT.md` 收工表加第 6 条，并做了两处限定，免得它变成每次都跑的无意义动作：
- 第 5 步（网络不通、凭据没配）可以跳；
- **第 6 步只在动过会发布的东西时才做**——纯改 `process/` 档案库不用验线上。
否则清单会退化成"每次都要做的五件半"，而**清单越臃肿，越容易被整体跳过**。

`process/开场白.md` 的日常版与老设备同步话术里，收工段都同步加了这一句。

### 追加（当天傍晚五轮）· hook 的自动 push 会静默失败，已加代理重试；「验线上」扩为「验线上 + 验推送」

**起因（很讽刺也很有价值）**：Andy 说「开场白第三点还是没加入」——我查文件，第三节早就写好并在远端
（`git show origin/main:process/开场白.md` 有）。但他这么一说就露了另一件事：
**我连着两个 commit（`863dd39`、`c6a0459`）本地提交成功，自动 push 却一直失败——
本地落后线上两个提交，而我以为推上去了。**

查 `.git/autosync.log`：

```
push 失败：fatal: unable to access '...': Empty reply from server
push 失败：fatal: unable to access '...': CONNECT tunnel failed, response 502
```

两行 curl 判定（走代理 000 / 绕过代理 200）确认：**本地代理挂了**，就是 `MIGRATION.md` 第三节第四步。
hook 当时只打印提示、不重试，于是「自动 push」在最需要它的时候哑火，而且**它不喊**——
工作区一样干净，日志在 `.git/hooks/` 里，人根本不会去看。

**修法（改的是 hook 生成源 `scripts/install-git-hooks.sh`，重装生效）**：
`do_push` 失败后先跑那两行 curl 判据，确认是本地代理挂了就 **自动用 `env -u ...` 绕开代理重试一次**，
再失败才提示。已在本机端到端验过：代理现在是坏的，提交时 hook 自己绕开代理推成功了。

**契约同步改了一条**：收工第 6 步从「验线上」扩成「验线上 + **验推送**」——
收工顺手 `git log --oneline -1` 与 `origin/main` 对一下，不一致就说明推送静默失败。
这条不是锦上添花：**「自动」的前提是失败要能看见，而 push 失败恰好是最会静默的那种。**

**方法论**：凡是「自动」的东西，都要问一句**它失败的时候会不会说话**。
自动 pull 失败你会撞上冲突，看得见；自动 push 失败你只会以为搞定了——
所以自动 push 必须自带重试或自带可见的失败信号，否则它比手动还危险。

**隔离验证（/tmp 建了个假仓库，验完已删）**：remote 是本地路径时 push 永远不会失败，走不到重试分支；
改成 git/curl 双 shim（**第一次 push 返回 CONNECT 502、之后放行；curl 走代理 000、绕过代理 200**）
再 commit，日志明文出现：

```
本地代理看着挂了（走代理不通、绕过代理通），绕开代理自动重试一次
```

判据触发 + 重试命令执行，命中。测完删了 `/tmp/autotest-*`，本机仓库未受影响。

踩到的测试坑（记一下，下次别重来）：
1. `ln -sf <hook> /dev/null` 之后再 `printf` 写它会**写进 /dev/null**——测试仓库的 hook 被我这么废掉一次。
2. 核心脚本要放 `.git/hooks/git-autosync.sh`（入口里是 `dirname $0/git-autosync.sh`），
   我一开始 cp 到 `.git/` 根下，hook 找不到。

### 追加（当天傍晚六轮）· 「验线上」从一句话变成一条命令 scripts/verify-online.sh

Andy 又把「每次做完要验证线上有没有生效」说了一遍——**上一轮已经加进契约第 6 步、也写进了开场白，
他还是要说，说明那句话没起作用**。回头看它的形态就明白了：

> 它是**一条写在文档里的规定动作**，执行它靠的是「记得」。
> hook 那次是同一个病根：写在文档里的自动机制，只在你想起它的时候才存在。

所以这轮不动措辞，动形态——把 `workflows.md` 第三节那三步 curl 收成一个脚本：

```
bash scripts/verify-online.sh <slug或完整URL> "这次改动的关键文本" --wait 120
bash scripts/verify-online.sh --push
```

四条设计取舍（都是被此前踩坑逼出来的）：
1. **带 `--wait`**：GH Pages 有 10 分钟缓存，push 成功那一刻去查，多半还是旧内容——
   不等待的验线等于骗自己「验过了」。
2. **退出码可串链**：非 0 就是没生效，能直接并进别的命令或判断里。
3. **网络不通要说「没验成」**，不能报「内容缺失」——两者混在一起，最坏的结果是
   把网络问题汇报成「线上没上线」，然后有人去改没坏的东西。
4. **文本核查会连 bundle 一起查**：首页 HTML 里没有时，去首页引用的 js bundle 里找；
