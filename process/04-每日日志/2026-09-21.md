## 身边的英语 · Kokoro 二次排障（用户反馈「还是很生硬」）
- **实测确认引擎此前根本没起来**：浏览器请求列表显示 transformers.js 仍在直连 `huggingface.co` 拉 config/tokenizer（三条全失败），catch 到 `TypeError: Failed to fetch` → 回退系统语音。jsDelivr 全部 200 可用。
- **根因1（已修）**：kokoro-js 里 voices 地址是**硬编码** `https://huggingface.co/.../voices/${e}.bin`，env 配置改不掉；且 `kmod.env.allowRemoteModels/localModelPath` 对 transformers 未生效。
  修法：加载前**拦截 window.fetch**，把含 `huggingface.co` 且匹配 `/Kokoro-82M-v1\.0-ONNX\/(?:resolve\/[^/]+\/)?(.+)$/` 的请求重写到 `/english/models/onnx-community/Kokoro-82M-v1.0-ONNX/$1`。实测请求列表已不再出现 HF，全部走本站。
- **根因2（已修）**：`dtype:"q8"` 时 transformers 实际请求的是 **`onnx/model_quantized.onnx`**（不是 model_q8.onnx），由 config.json 决定。CI 落地文件名已由 model_q8.onnx 改为 model_quantized.onnx，并加 100MB 上限。
- **根因3（未解，核心瓶颈）**：模型 92MB 从 GitHub Pages 下载，**实测仅 34 KB/s**（10 分钟只下 20.5MB，全量约 45 分钟）。用户（国内）几乎不可能等到加载完成 → 一直用 fallback 系统语音 → 听感仍生硬。
- 结论：代码链路已全部正确（config/tokenizer/model 均 200 同源加载），**剩余问题是托管带宽，不是代码**。待与用户确认换国内可达的高速托管（腾讯云 COS/CDN 或 CloudBase 存储）。

## 身边的英语 · Kokoro 三次排障：找到瓶颈并彻底解决（已跑通）
- **真正的瓶颈是托管带宽，不是代码**：92MB 模型从 GitHub Pages 下载实测仅 **34 KB/s**（10 分钟只下 20.5MB，全量约 45 分钟），用户永远等不到引擎就绪 → 一直回退系统语音 → 听感生硬。
- **解法：改从国内镜像 hf-mirror.com 加载**。同文件实测 **7.1 MB/s**，92MB 仅 **12.9 秒**下完，且返回正确 CORS 头（`access-control-allow-origin` 回显 Origin），模型和 voices 均可跨域直取。
  - 关键前提：必须用**正确文件名** `onnx/model_quantized.onnx`。此前以为镜像不可用，是因为请求的是仓库里根本不存在的 `model_q8.onnx`（404）。
- fetch 重写规则改为：`huggingface.co/.../Kokoro-82M-v1.0-ONNX/...` → 优先 `https://hf-mirror.com/onnx-community/Kokoro-82M-v1.0-ONNX/resolve/main/...`，失败回退本站 `/english/models/...`（兜底，34KB/s 仅应急）。
- 另加 `from_pretrained` 的 `progress_callback`，底部状态位显示「配音模型下载中… N%」。
- **验证结果**：reload 后 20 秒内 `✓ 地道美音引擎已就绪（Kokoro 神经 TTS）`；端到端合成 `GEN_OK samples=74400 sr=24000`（3.1 秒 24kHz 音频），voices 确认可从镜像加载。
- 提交 4110fdc 已推送。

### 经验（可复用）
- 浏览器端大模型的首要风险是**托管带宽**，不是代码正确性；选型前先测目标托管的实际下载速度。
- 第三方库把资源地址**硬编码**（如 kokoro-js 的 voices 写死 huggingface.co）时，env 配置改不掉，最可靠的办法是**在加载前拦截 window.fetch 做 URL 重写**，并可做「主源 + 兜底源」的双路 catch。
- transformers.js 的 dtype→文件名映射以 config.json 为准（q8 实际对应 model_quantized.onnx），不要凭约定猜文件名。
- 校验下载结果必须设**体积区间**（如 10MB~100MB），仅用 `-s`（非空）会让 HF 的 "Entry not found" 之类错误响应蒙混过关。
