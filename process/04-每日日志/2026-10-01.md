## 主任务：身边的英语「等一会才有声、不够顺滑」—— 判定为架构问题，整条音频链路重做

**Andy 的反馈**：直开 <https://linqiongni.top/english/index.html?diag=1> 点播放，**等一会才有声音，不够顺滑**。
截图的诊断面板把根因摊开了：

```
audPlay: 起播 audio/s20.mp3 @0s rate=1
watchdog: 4s 未推进 -> 回落系统语音
系统语音: 整段 speak 30 句
audPlay: 起播 audio/s11.mp3 ...        ← 两套声音先后都响
```

**根因（不是弱网，也不是文件静音）**
1. 一篇 = 一个 ~1MB 整篇 MP3，点播要等缓冲到句起点才出声，弱网要几十秒静默；
2. 期间 4s 看门狗见 `currentTime` 不动就切**系统语音**（生硬卡顿的真正来源），
   MP3 缓冲够了自己又响 → 人声与合成音抢喇叭，前后错位 = "等一会才有声、听着生硬"。

**改造：句级小文件 + 双缓冲（一次改到底，不再打补丁）**
- 生成：每句一个 ~30KB MP3（`audio/<sid>/uNNN.mp3`，句尾接 220ms 静音，念不出的中文句照旧静音占位）。
  `audio/index.js` 结构 `{f,off,d}` → **`{seg:[...], len:[...], d}`**（seg 句文件路径、len 每句时长含尾静音）。
- 播放：两个 `<audio>` 交替（k 号只播 `句号%2==k`），切句 = 换一个已预热的缓冲直接 play，
  **不再在同一元素上 seek**（seek 才是起播卡顿的根源）。备用缓冲永远预载下一句。
- 句尾 220ms 静音把切换间隙（<50ms）盖住，听起来是连续的一整段。
- **彻底删除「静默 4s 切系统语音」**：宁可提示"再点一次"，也不让两套声音抢喇叭。
- 新增**按句长的定时推进兜底**（`audNext` + `audStepT`）：iOS Safari 的 `ended` 偶发不触发，
  没有这道兜底整篇会卡死在第一句。

**踩到的三个坑（都是本机环境坑，记下来）**
1. **safe-delete 批量保护会直接打断生成进程**：`os.remove()` 删旧整篇 MP3 时触发
   `[SAFE_DELETE_BULK_CONFIRM_REQUIRED]`（本 turn 累计 50 次删除），生成跑到一半崩。
   改法：旧整篇 **shutil.move 进 `.tts_cache`**（不是删，同样能离开 audio/ 不入 git、不被 rsync 同步）。
   → 以后凡是"清理自己刚生成的中间产物"，一律用 move，别用 remove/rm。
2. **后台 `nohup ... &` 的日志会被缓冲吞掉、进程还会被收走**：改成前台跑 `-u`（无缓冲）+ 显式 timeout，
   一眼看到全部进度。以后重跑这类脚本直接前台。
3. `grep -c "a|b"` 在 BSD grep 必须 `-E`（老条，又踩）。

**验证**（本机媒体时钟已坏，`ended`/`currentTime` 推进在本机不可信，所以换测法）
- CDP 无头实测：点击播放 → `audPlay: 起播 句1/30 audio/s01/u001.mp3`（不再 seek 整篇 ✓）→
  `句1 定时推进（ended 没来）` → `句1 播完 -> 接句2` → `接句3`，状态行跟到「第 3 句 / 共 30 句」。
- 线上：`audio/s01/u001.mp3` 200 / `audio/index.js` 200（新结构）/ 旧整篇 `s01.mp3` **404**（仓库少 25MB）。

## 追加（11:30）· Andy 反馈「播放出来的音频和文字不对应」—— 查了两层，改了三处

**先排掉的假嫌疑**：整条链路的句序是 100% 对齐的。用 `.tts_cache/<sid>_NNN.txt`（送进 edge-tts 的原文）
逐句比对 `splitSents()` 在页面上切出的句子：28 篇 820 句，0 处不一致、0 处句数不符。
所以**不是音频生成错位**，别往 `gen_english_audio.py` 上找。

**真凶（两处，都跟「嵌入态」有关）**
1. **点任意一句 = 从那句一路连播到篇尾**（`playFrom(i)` 里 `audPlay(i, false)` 的 false 被写死）。
   页面页脚明明写着「点任意一句可从该句跟读」，实际点第 2 句会从头念下去 —— 声音和高亮一起跑远，
   点的人感觉就是「音频和文字对不上」。
   → 修：`playFrom(i, one)` 把 oneShot 透传，点句走 `playFrom(i, true)`，念完一句就停；
     底部 ▶ / 「播放这一篇」仍是整篇连播。
2. **高亮跟随时用 `behavior:"smooth"`**。子站嵌进主页 tab 后，父容器（主站 `.page-scroll`）会把
   平滑滚动搅断，高亮句滚出视野 → 视觉上「文字停在开头，声音在念后面」， Andy 的截图正是这个状态。
   → 修：新增 `ensureVisible()`，越界即**瞬时**滚到视野中上部 + 260ms 二次复核（防父容器又拽回去）；
     顺手把切篇滚顶的 2 处 smooth 也换掉（embed 里同样会失效）。

**验证**：CDP 实测（本地 8899 起 python http.server）连播 30 秒，main 滚量 0 → 394，
高亮句 top 始终在 275~627（视口 757）之间，即**每一句都留在视野里**。JS 语法体检 OK，rsync + 主题金本注入后 public 副本 grep 复核一致。

**教训（写下来，下次直接查这两处）**：静态站子站只要嵌在 iframe 里，凡是
`behavior:"smooth"` / `scrollIntoView({behavior:"smooth"})` 都可能被父容器搅断 ——
